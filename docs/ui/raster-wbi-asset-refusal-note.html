Option A — each refusal gets the note about its own kind, once each (recommended)

One file with an unsupported asset field and an unsupported loop. Both are refused in the same run.

Both refusals in one run

$ rasterc title.raster error: only `kind: background` is supported yet --> title.raster:3:48 | 3 | asset image hero = png("art/hero.png") { kind: sprites palette: auto(4) dedup: true } | ^^^^^^^ only `kind: background` is supported yet = note: this release reads one kind of asset: `asset image` from a `png`, with `kind: background`, `palette: auto(4)` and `dedup: true`, used through `.tiles`, `.nametable`, `.attributes` and `.palette` error: `loop` is not supported yet --> title.raster:9:5 | 9 | loop {} | ^^^^^^^ `loop` is not supported yet = note: this release compiles `main`, `fn`, `if`, `while`, `for`, u8 arithmetic, and `ppu.*` / `mmc3.*` register writes; timed blocks with `cycles`, `pad`, `sync exact` and `wait cycles`; and one `frame` of `every ... scanlines` events error: could not compile title.raster (2 errors)

Each note sits beside the first refusal it explains, and is not repeated. Two notes in one run is a little more to read, but the loop refusal still says what the release does compile.

Refusing a correct asset

This refusal comes from an asset that is written exactly as the release allows. A note listing what is allowed would describe the very line they wrote, so it says nothing new. It goes away once pictures reach the ROM.
