The agreed rule for a ppu.data read

$2007 reads through the PPU’s buffer: it hands back the byte the previous read fetched and loads the byte at the current address for the next read. So one read returns the wrong byte, and the two-read idiom — discard the first, keep the second — returns the right one.

What was chosen, and over what

rasterc warns on a lone read and stays silent on a pair, and refuses a compound assignment outright. Rejected: warn on every read, which warns twice on the correct idiom on every build with nothing in this release to silence it; and refuse every read, which would remove VRAM reads from the language — peek/poke are specified (§9.2) but not implemented, and asm is refused, so there is no escape hatch. Emitting the dummy read for the author was ruled out by the decision already recorded in .cerebro/traps.md: a compiler that inserts PPU accesses the source did not ask for is a compiler whose cycle counts you cannot trust.

The rule, in one sentence

A ppu.data read warns unless the statement immediately before it, or the statement immediately after it, in the same block, also reads ppu.data. A single statement that reads it twice counts as its own neighbour. Nothing else counts — not the PPU address, not what the source does with the byte.

1 · The pair — silent

var discard: u8 = ppu.data var tile: u8 = ppu.data
(nothing)

2 · Three or more in a row — silent, all of them

var a: u8 = ppu.data var b: u8 = ppu.data var c: u8 = ppu.data
(nothing)

Reading a run of VRAM bytes is exactly this shape: prime once, then one read per byte. Every read after the first is correct, and the first is the deliberate discard.

3 · Two reads in one statement — silent

var sum: u8 = ppu.data + ppu.data
(nothing)

Two LDA $2007 are emitted in order, so this is the idiom written on one line. The rule is about the reads, not about what the source then does with them.

4 · Separated by anything at all — both warn

var a: u8 = ppu.data ppu.addr = $20 var b: u8 = ppu.data
warning: ... at 1:17 warning: ... at 3:17

Correct here: the address moved between them, so the second read really is unprimed. rasterc is not reasoning about the address — it warns because neither read has a neighbour, and it would warn the same way if the middle statement were harmless.

5 · Across a block boundary — both warn

if ready { var a: u8 = ppu.data } var b: u8 = ppu.data
warning: ... at 2:21 warning: ... at 4:17

Adjacent on the page, not adjacent in the emitted code: a branch runs between them, so the first read may not have happened at all. A neighbour never crosses a { } — the same for a cycles(...) region, a while body and a frame event. A read in a global var initializer has no neighbours either, and always warns.

6 · A refused compound assignment beside a read — the read still warns

ppu.data += 1 var a: u8 = ppu.data
warning: ... at 2:17 (the read: its neighbour was refused, so it has none) error: ... at 1:5 (the compound assignment)

The build fails on the error either way, and warnings print before errors — so one run shows the author both things rather than two runs showing one each.

7 · A read on the only line of main — warns

main { var a: u8 = ppu.data }
warning: ... at 2:17

No statement before it and none after it, so no neighbour. Nothing special-cases the edges of a block.

8 · The whole run, when it succeeds
