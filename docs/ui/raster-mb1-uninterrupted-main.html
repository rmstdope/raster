raster-mb1 — nothing interrupts main, and what pins it

Agreed with the navigator over two rounds. The bead was filed as a warning: a frame handler leaves main's MMC3 bank selection changed, so main's next mmc3.bank_data write lands on a register nobody named. That cannot happen in this release, and the evidence is below. What ships instead is the thing that was actually missing: two tests that pin the invariant, and a paragraph of specification telling an author what they may rely on. No diagnostic changes.

1 · The program the bead says compiles silently and is wrong

main { mmc3.bank_select = 0 mmc3.bank_data = 3 } frame bars using timed { every 8 scanlines from 0 to 239 { mmc3.bank_select = 6 } }
Compiled demo.raster -> demo.nes mapper MMC3 (4), NTSC prg 32 KiB, 4 banks of 8 KiB fixed $E000-$FFFF, 6357 of 8186 bytes used

It does compile silently, and it is right to. mmc3.bank_data = 3 lands on R0, exactly as the line above it says.

5 · The cross-handler direction is real, and already warned

A handler does leave its selection behind for the next handler. rasterc already covers it: every handler body starts its bank tracking at unknown, so a mmc3.bank_data in a handler that did not select first already earns this.

frame bars using timed { at scanline 32 { mmc3.bank_select = 6 } at scanline 64 { mmc3.bank_data = 1 } }
warning: rasterc cannot tell which bank register this write lands on --> demo.raster:3:22 | 3 | at scanline 64 { mmc3.bank_data = 1 } | ^^^^^^^^^^^^^^^^^^ a frame handler runs with any register selected = note: R6 and R7 are the two 8 KiB PRG windows; a write landing on either one repoints $8000 or $A000 = note: selecting with a literal 0 to 5 in the handler, before the write, keeps the map reset chose

There is no silent case anywhere. The analysis raster-rid shipped is already right for this release.

6 · What ships — the new final paragraph of spec §9.4

It goes between the existing bank-warning paragraph and the rasterc today: as designed line. Chosen over a shorter version that left NMI unmentioned, and over a version phrased as a promise — this describes what the release does, so a later release that unmasks interrupts during main changes a stated fact rather than breaking a guarantee.

Nothing runs between two of `main`'s statements. Reset masks IRQs with `SEI` before your program starts, and the `CLI` that arms an IRQ chain is emitted after `main`'s last statement — a `timed` frame arms no interrupt at all. NMI is the one interrupt the flag cannot mask, and `$FFFA` points at an `RTI` in the runtime for every program this release builds, so enabling NMI through `ppu.ctrl` runs none of your code. A `mmc3.bank_select` and the `mmc3.bank_data` write that follows it are therefore always consecutive. Handlers are a different matter. They run in schedule order and each leaves its selection behind for the next, so rasterc treats every handler as starting with no register it can name.

7 · What ships — the two tests, and what they say when they fail

The invariant has two halves that break independently, in two crates. The failure messages were chosen long on purpose: the message is the only place the reasoning lives, and the person who reads it is mid-change and least inclined to go looking.

crates/raster-codegen/tests/generate.rs

thread 'nothing_unmasks_irqs_before_main_has_run' panicked at ... a `CLI` is emitted at item 41, before `main`'s halt label at item 63. rasterc's MMC3 bank tracking assumes nothing runs between two of `main`'s statements: it folds a `mmc3.bank_select` and judges the `mmc3.bank_data` write that follows it against the register that select named. If interrupts are unmasked while `main` is still running, a `frame` handler's own bank select can land between the two and the write moves a window the author never named — silently, because the tracking still believes the fold. That needs a warning before this change ships. Spec section 9.4 says `main` is uninterrupted; either that paragraph changes with this, or this does not ship.

crates/raster-link/tests/runtime.rs

thread 'the_nmi_vector_is_always_the_runtimes_own_handler' panicked at ... $FFFA resolved to $E0C4, where the byte is $4C, not the runtime's `RTI`. NMI is the one interrupt the I flag cannot mask, so a program can take one at any point in `main` by setting bit 7 of `ppu.ctrl`. That is safe today only because $FFFA runs none of the program's own code. Pointing it anywhere else means a handler can run between two of `main`'s statements, which spec section 9.4 says cannot happen — and which rasterc's MMC3 bank tracking relies on. See `nothing_unmasks_irqs_before_main_has_run` in raster-codegen.
