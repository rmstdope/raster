What the MVP demo ships as

Planning raster-fl4.5 (P0). The bead is milestone M8 of docs/raster-mvp-plan.md — “the full MVP demo from spec §13” — and it is not one bead. Two implementers have handed it back. Below are three things the demo could ship as, what each proves, and what each costs. The choice is yours; the split into beads afterwards is mine.

00 · Why section 13 cannot be built as written

The spec says of its own example: “This is the program the MVP must compile — not one that compiles today.” That is true, and it understates it. Two names in the example are declared nowhere — not in the example, not in the compiler, not elsewhere in the spec:

for i in 0..240 { raster.bars[i] = sine_table[i] & $E0 // sine_table is never declared } ... cycles(<= 28) pad { ppu.mask = $1E | raster.bars[line] // `line` is not a builtin anywhere }

Verified: grep '"line"' across the compiler matches only parser tests, and neither raster-sema nor raster-ir binds it. Both would fail with unknown name (crates/raster-sema/src/lib.rs:656). So section 13 needs a spec decision before it needs code, whichever option you pick — unless you pick one that does not use them.

01 · Where the compiler actually is

Much better than raster-fl4.5’s plan assumes. Stable IRQ-timed colour bars already run and are pinned to frame 300 in the emulator (crates/rasterc/tests/emulator.rs:187).

OPTION A

Section 13, in full

The demo the spec and the MVP plan describe: a PNG background, and a per-scanline emphasis value read out of a 240-byte table in RAM.

target nes { mapper: mmc3 prg: 128K chr: 128K region: ntsc } asset image picture = png("art/picture.png") { kind: background palette: auto(4) } chrrom bank 0 { picture.tiles } group raster { var bars: [240]u8 in bss } frame main using irq { every 1 scanlines from 0 to 239 { cycles(<= 28) pad { ppu.mask = $1E | raster.bars[line] } } }

What it needs first

Arrays and indexed reads · a BSS allocator (the zero page is the only arena today, and 240 bytes will not fit) · group members · in bss · wait vblank · loop · the asset pipeline wired into rasterc · chrrom and real CHR ROM in the linker (which hardcodes CHR RAM today) · target honoured for prg: 128K (the linker hardcodes 32 KiB) · a line builtin and a sine_table answer in the spec.

~12 beads   Proves A1–A7 in full. The demo is the one the documents promise.

OPTION B

The image, with bars the compiler can already place

Keeps the MVP’s one-sentence goal intact — “displays an image imported from a PNG with the background colour changing at chosen vertical positions” — but places the bars with the at scanline handlers that work today instead of a RAM table.

target nes { mapper: mmc3 region: ntsc } asset image picture = png("art/picture.png") { kind: background palette: auto(4) } chrrom bank 0 { picture.tiles } main { load_palette(picture.palette) load_nametable(picture.nametable, picture.attributes) ppu.ctrl = $08 ppu.mask = $1e } frame main using irq { at scanline 60 { ppu.mask = $3e } // red emphasis at scanline 120 { ppu.mask = $5e } // green at scanline 180 { ppu.mask = $1e } // none again }

What it needs first

The asset pipeline wired into rasterc · chrrom and CHR ROM in the linker · a minimal target block · the two load builtins. No arrays, no BSS, no loop, no line, no spec change.

~5 beads   Proves A1–A7. Section 13’s per-scanline table becomes a later epic rather than a blocker.

OPTION C

The timing demo now, the image next

Promote the fixture that already works to examples/mvp/, add the budget table, and put it on your console. No image.

main { ppu.addr = $3f ppu.addr = $00 ppu.data = $0f ppu.ctrl = $08 // background $0000, sprites $1000: A12 rises every scanline ppu.mask = $1e } frame bars using irq { at scanline 60 { ppu.mask = $3e } at scanline 120 { ppu.mask = $5e } at scanline 180 { ppu.mask = $1e } }

What it needs first

Only raster-5vk (the budget table) and a hardware run. This program compiles and runs on main today.

~2–3 beads   Proves A1, A2, A4, A5, A6, A7. Does not prove A3 — there is no image, so the MVP’s own sentence is not met.

03 · The hardware gate, on a PAL console

Separate question, and it applies to every option above. The compiler, the spec and the emulator are all NTSC (raster-emu is hard-wired NesRegion::Ntsc); the MVP plan puts PAL out of scope; your console is a PAL NES. On raster-20i.4 you already chose to accept PAL evidence rather than rerun NTSC, and that decision is what A7 now has to be read against.

What PAL hardware can and cannot settle
Bar placement — the MMC3 counter clocks on filtered PPU A12 rises, so at scanline 60 is scanline 60 on either regionholds on PAL
Boot, mapper, CHR bank init — what an emulator cannot prove, since it powers every MMC3 register up at zeroholds on PAL
Cycle windows — IRQ_HANDLER_BODY_CYCLES = 9 was measured on NTSC; PAL runs 3.2 dots per CPU cycle, not 3NTSC number
A using timed frame — spends a whole frame of counted cycles; PAL has 312 scanlines, not 262wrong on PAL

So an using irq demo is largely region-tolerant and a using timed one is not — which is reasoning from the constants, not something anyone has run. Whether that is good enough for A7, or whether the compiler should learn region: pal, is the second question.
