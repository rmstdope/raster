Option A — the PAL swap is said where the tints are

The whole demo as agreed so far: test card, red/green/plain bars at 60/120/180, at examples/mvp/demo.raster. On a PAL console the NES's red and green tint bits are swapped, so the second band shows red and the first green. Here the source says so beside each tint, and the README says so too.

What the developer sees in the emulator

examples/mvp/demo.raster, every word as it ships

// The MVP demo: a picture imported from a PNG, with colour // bars that start on chosen lines of the screen. // // art/picture.png is a test card. The yellow numbers on its // ruler mark lines 60, 120 and 180: each tint should start // exactly on its mark. Build it with // // rasterc examples/mvp/demo.raster // // and open demo.nes in an emulator. target nes { mapper: mmc3 region: ntsc } asset image picture = png("art/picture.png") { kind: background palette: auto(4) } chrrom bank 0 { picture.tiles } main { load_palette(picture.palette) load_nametable(picture.nametable, picture.attributes) ppu.ctrl = $08 // background tiles from $0000, sprites from $1000 ppu.mask = $1e // rendering on, no tint } frame bars using irq { at scanline 60 { ppu.mask = $3e } // red tint (green on a PAL console) at scanline 120 { ppu.mask = $5e } // green tint (red on a PAL console) at scanline 180 { ppu.mask = $1e } // no tint again }

The README section

## The MVP demo `examples/mvp/demo.raster` shows a picture imported from a PNG, with the background tinted red from line 60, green from line 120, and back to plain from line 180. rasterc examples/mvp/demo.raster Open `examples/mvp/demo.nes` in Mesen2. Each tint starts on its yellow mark on the ruler down the left edge; the build prints how many cycles each bar's handler has to spare. On a PAL console the red and green tints swap places: the console wires those two bits the other way round.
