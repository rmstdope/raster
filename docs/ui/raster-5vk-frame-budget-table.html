raster-5vk — the frame strategy and its per-event budget table

Agreed with the navigator in the UX stage. The table of spec section 7.2 follows the build summary, with a heading that names the frame and its strategy. Section 7.1 now says an omitted using always means timed. New lines are in cyan. Summary figures come from real builds on main at 48bb178. Handler costs are real: a constant ppu.mask store is 6 cycles, one store from a variable is 7, and the two-statement handler is 12. The irq window is the 9-cycle hblank, and the timed window is one 114-cycle scanline.

01 · using irq, everything fits

frame bars using irq { at scanline 60 { ppu.mask = $1f } every 8 scanlines from 96 to 200 { ppu.mask = $1e } } $ rasterc bars.raster Compiled bars.raster -> bars.nes mapper MMC3 (4), NTSC prg 32 KiB, 4 banks of 8 KiB chr 8 KiB RAM fixed $E000-$FFFF, 629 of 8186 bytes used yours 497 bytes runtime 132 bytes, the reset sequence around your program entry reset $E000, nmi $E274, irq $E271 frame bars (using irq, mmc3) scanline 60 handler 6 cycles window 9 3 spare scanline 96-200 every 8 handler 6 cycles window 9 3 spare

An every is one row, named the way the source names it. The handler runs the same code on every scanline and is already charged its worst case, so no figure is hidden.

02 · No using: timed, and it says so

frame bars { at scanline 60 { ppu.mask = $1f } every 8 scanlines from 96 to 200 { ppu.mask = $1e } } $ rasterc bars.raster Compiled bars.raster -> bars.nes mapper MMC3 (4), NTSC prg 32 KiB, 4 banks of 8 KiB chr 8 KiB RAM fixed $E000-$FFFF, 3341 of 8186 bytes used yours 3209 bytes runtime 132 bytes, the reset sequence around your program entry reset $E000, nmi $ED0C, irq $ED0C frame bars (using timed by default, mmc3) scanline 60 handler 6 cycles window 114 108 spare scanline 96-200 every 8 handler 6 cycles window 114 108 spare

With using timed written out, the heading reads frame bars (using timed, mmc3). An omitted using never turns into irq, however well the schedule would fit.

05 · A handler over its window

frame bars using irq { at scanline 60 { ppu.mask = $1f ppu.scroll = 0 } every 8 scanlines from 96 to 200 { ppu.mask = $1e } } $ rasterc bars.raster error: an `irq` handler exceeds its hblank --> bars.raster:6:5 | 6 | at scanline 60 { | ^^^^^^^^^^^^^^^^ handler costs 12 cycles, the hblank leaves 9 = note: the MMC3 asserts its interrupt near the end of the scanline before the one this handler runs on, so a store made once the window has closed lands part-way along a visible row = note: split the work across two events on consecutive scanlines to give each a window of its own, or use `using timed`, which gives a handler the whole scanline at the cost of the frame's entire CPU time frame bars (using irq, mmc3) scanline 60 handler 12 cycles window 9 OVER BY 3 scanline 96-200 every 8 handler 6 cycles window 9 3 spare error: could not compile bars.raster (1 error)

The error is unchanged. The table comes after the last diagnostic and before the count line, which stays last. Whether the error is the irq hblank one or timed block exceeds its budget, every handler that is over says OVER BY n, in words rather than colour.

06 · A failure that is not a handler overrun

$ rasterc bars.raster error: the program does not fit the MMC3 fixed bank = note: … error: could not compile bars.raster (1 error)

No table. A failed build prints it only when the failure is a handler over its window, so a half-measured table never appears.

What was considered and rejected

  • Event rows in the summary's label column (scanline 60: 6 of 9 cycles). It would have been one block, but the figures don't line up in columns, and it isn't the table the specification promises.
  • One row per scanline an every fires on. every 1 scanlines from 0 to 239 would print 240 identical rows for one line of source.
  • Letting the compiler choose when using is omitted (irq when it fits, otherwise timed, with the reason in the heading). One added statement could quietly move the program from irq to timed, taking the whole frame's CPU time while the build stays green.
  • Printing only the error when a handler overruns, as today. You couldn't see which other events had room, and the error itself tells you to split the work across events.
  • ok in the last column, the specification's word. You would have to subtract to find how much room is left, and that is the number you act on.
