The message is about the byte in the variable, not about the port. An author who has never heard of the PPU read buffer understands the first line; the notes teach the mechanism afterwards.

1 · The lone read

warning: this `ppu.data` read gives you the byte before the one you asked for --> vram.raster:5:20 | 5 | var tile: u8 = ppu.data | ^^^^^^^^ nothing next to this read primes the PPU's read buffer = note: $2007 hands back what the previous read fetched, and loads the byte at this address for the next read = note: read `ppu.data` twice in a row, discard the first and keep the second; a palette address, $3F00 to $3FFF, is not buffered and reads back at once

2 · The compound assignment

error: `ppu.data` cannot be the destination of a compound assignment --> vram.raster:12:5 | 12 | ppu.data += 1 | ^^^^^^^^ `+=` reads $2007 before it writes, and that read is buffered = note: the byte it would add to is the one at the previous address, not the one at the address you are writing = note: read the byte you want into a variable of your own, add to that, and write the whole value

3 · The spec, §9.5

| `ppu.data` | `$2007` | **allowed, and buffered** |

plus a paragraph under the table:

`ppu.data` reads back, but not the byte you just addressed. A $2007 read hands you the byte the previous read fetched and loads the byte at the current address for the next one, so a single read gives you the wrong byte and rasterc warns about it. Read it twice in a row — discard the first, keep the second — and rasterc is silent. Palette addresses, $3F00 to $3FFF, are not buffered and read back at once. A compound assignment is refused outright: `ppu.data += 1` reads $2007 for you, and there is no way to prime a read that happens inside a statement.
