raster-hkg — a timed frame cannot afford an NMI

Agreed with the navigator over three rounds. The bead was filed from the review of PR #50: §9.4 tells an author that enabling NMI “runs none of your code”, which reads as a green light, and nothing in the specification says a frame ... using timed is destroyed by one. What ships is a warning — the ROM is still written — and two paragraphs of specification. Every terminal block below is the layout rasterc actually prints.

1 · The program that compiles silently today

1 main { 2 ppu.ctrl = $88 // NMI on 3 ppu.mask = $1e 4 } 5 6 frame bars using timed { 7 every 8 scanlines from 0 to 239 { ppu.mask = $1e } 8 }

That ROM is wrong and nothing says so. A timed frame synchronizes once and never again: every position after it is a count of cycles forward from that one moment. $FFFA is the runtime's bare RTI, so none of the author's code runs — but the interrupt still costs 13 cycles (7 to enter, 6 for the RTI) once per frame, out of cycles the schedule had already allocated. The picture drifts by that much every frame and never comes back.

Decided: warn, and still build. Considered and rejected: refusing, which §6.4 argues for and which using irq's own PPU-configuration check already does — rejected because every other hazard rasterc can see but not prove is a warning, and a refusal blocks an author who is mid-edit and knows. Also rejected: specification text with no compiler change.

2 · The message

warning: this program enables NMI, and a `timed` frame cannot afford one --> demo.raster:6:18 | 6 | frame bars using timed { | ^^^^^ this schedule counts cycles from one synchronization onwards = note: `ppu.ctrl` holds $88 when the frame starts, and bit 7 is NMI; each NMI costs the schedule 13 cycles it has already spent = note: clear bit 7 to keep the schedule, or use `using irq`, which synchronizes on every scanline it fires Compiled demo.raster -> demo.nes mapper MMC3 (4), NTSC prg 32 KiB, 4 banks of 8 KiB chr 8 KiB RAM fixed $E000-$FFFF, 6357 of 8186 bytes used yours 6225 bytes runtime 132 bytes, the reset sequence around your program entry reset $E000, nmi $F8D4, irq $F8D4 warnings 1

The carets sit on timed, the span the compiler already carries for a frame's strategy and the one using irq's refusals point at. One warning per program, not one per ppu.ctrl write. The message names the schedule rather than the consequence; a draft leading with “NMI is on, and it will pull this frame off the picture” was rejected.

3 · With the using clause left off

An omitted clause means timed (§7.1), so the same program earns the same warning. There is no timed to underline, so the carets take the frame's first line.

warning: this program enables NMI, and a `timed` frame cannot afford one --> demo.raster:6:1 | 6 | frame bars { | ^^^^^^^^^^^^ this schedule counts cycles from one synchronization onwards = note: `ppu.ctrl` holds $88 when the frame starts, and bit 7 is NMI; each NMI costs the schedule 13 cycles it has already spent = note: clear bit 7 to keep the schedule, or use `using irq`, which synchronizes on every scanline it fires

4 · A value rasterc cannot fold

var flags: u8 main { ppu.ctrl = flags ppu.mask = $1e } frame bars using timed { every 8 scanlines from 0 to 239 { ppu.mask = $1e } }
warning: rasterc cannot tell whether this program enables NMI --> demo.raster:8:18 | 8 | frame bars using timed { every 8 scanlines from 0 to 239 { ppu.mask = $1e } } | ^^^^^ this schedule counts cycles from one synchronization onwards = note: the last write to `ppu.ctrl` before the frame is not a value rasterc can see, so bit 7 is unknown = note: bit 7 is NMI, and each NMI costs the schedule 13 cycles it has already spent; writing a constant with bit 7 clear keeps it

Decided: say so rather than stay silent, the shape mmc3.bank_select already uses for an unfoldable value.

5 · Written on some paths and not others

main { if x { ppu.ctrl = $08 } ppu.mask = $1e } frame bars using timed { every 8 scanlines from 0 to 239 { ppu.mask = $1e } }
warning: rasterc cannot tell whether this program enables NMI --> demo.raster:6:18 | 6 | frame bars using timed { every 8 scanlines from 0 to 239 { ppu.mask = $1e } } | ^^^^^ this schedule counts cycles from one synchronization onwards = note: `ppu.ctrl` is written on some paths through this program and not others, so bit 7 is unknown = note: bit 7 is NMI, and each NMI costs the schedule 13 cycles it has already spent; writing a constant with bit 7 clear keeps it

Decided: its own first note, mirroring what using irq already distinguishes. One sentence covering both reasons was rejected: they are two different things for the author to go and fix.

6 · A handler turns NMI on

1 main { 2 ppu.ctrl = $08 // NMI off: main is clean 3 ppu.mask = $1e 4 } 5 6 frame bars using timed { 7 every 8 scanlines from 0 to 239 { 8 ppu.ctrl = $88 9 } 10 }

Decided: in scope. The program-level check reads what ppu.ctrl holds when the frame starts, and sees nothing here — main is clean. A handler write is worse than a clean one in main: NMI goes on for every frame after the first.

warning: this write enables NMI, and a `timed` frame cannot afford one --> demo.raster:8:9 | 8 | ppu.ctrl = $88 | ^^^^^^^^^^^^^^ bit 7 is NMI, and this handler runs on every frame = note: the schedule is counted from one synchronization and never re-checked; each NMI costs it 13 cycles it has already spent = note: clear bit 7 to keep the schedule, or use `using irq`, which synchronizes on every scanline it fires

“this write” and not “this program”: the carets are on the write, and two warnings on one build must not read as the same one printed twice.

A handler write rasterc cannot fold gets the same treatment as one in main:

warning: rasterc cannot tell whether this write enables NMI --> demo.raster:7:9 | 7 | ppu.ctrl = flags | ^^^^^^^^^^^^^^^^ this is not a value rasterc can see, so bit 7 is unknown = note: bit 7 is NMI, and this handler runs on every frame; each NMI costs the schedule 13 cycles it has already spent = note: writing a constant with bit 7 clear keeps the schedule

A handler is straight-line — if, while, for and calls are all refused inside a timed region — so a handler write is either a constant or unfoldable. There is no conditional case inside one.

7 · Order in the output

The program-level check needs the whole program lowered, so it runs after lowering and its warnings are appended: a program that also trips a bank-select or $2007 warning prints those first and the NMI ones last, whatever the line numbers say. The frame-level warning comes before any handler one, and handler warnings follow schedule order.
