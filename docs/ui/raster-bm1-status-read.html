The agreed rule — a $2002 read and the PPU write latch

What rasterc does about reading ppu.status. Agreed with the navigator over four rounds, from eight mockups. Every program on this page compiles clean and exits 0 on main today; the ones marked warns are diagnostics being added on purpose.

Two rules, both about a sequence, both warnings.

1 — the latch. Walking the statements of one block in order, rasterc tracks whether a ppu.addr or ppu.scroll pair is half written: those two registers share one write latch, so an odd number of writes to either leaves the PPU expecting a second half. If a $2002 read happens there — a ppu.status read in the source, or the poll that sync exact compiles to — the latch goes back to its first write and the rest of the pair is taken as another first half. That warns.

2 — the flag. A ppu.status read whose very next statement in the same block is sync exact warns: the read has taken the vblank flag the poll spins on, so the sync waits for the next frame instead of this one.

Neither rule crosses a { }, and neither crosses a call. The tracking restarts closed inside every nested block, and goes back to closed after one — so rasterc can miss a real break and can never invent one.

1 · A read inside an address pair — warns

main { ppu.addr = $3f var s: u8 = ppu.status ppu.addr = $00 ppu.data = $21 }

Warns (rule 1). The ROM is still written and the summary counts the warning.

2 · sync exact inside an address pair — warns

main { ppu.addr = $3f sync exact ppu.addr = $00 }

Warns (rule 1), with its own message naming sync exact. There is no $2002 anywhere in this source — sync exact compiles to BIT $2002 / BPL — and the program is broken. This is the case the bead was filed for.

3 · A read before a complete pair — silent

main { var s: u8 = ppu.status ppu.addr = $3f ppu.addr = $00 }

Silent. This is the idiom: put the latch in a known state, then write both halves.

4 · A flag read nowhere near a pair — silent

main { ppu.mask = $1e var hit: u8 = ppu.status if hit >= $40 { ppu.mask = 0 } }

Silent. Reading $2002 for sprite 0 or the overflow flag is what the register is for.

5 · A read directly before sync exact — warns

main { var s: u8 = ppu.status sync exact cycles(20) pad { ppu.mask = $1e } }

Warns (rule 2). The ROM runs; it is a frame late, every time.

6 · A pair broken across a { } — silent

main { ppu.addr = $3f if flag > 0 { var s: u8 = ppu.status } ppu.addr = $00 }

Silent, deliberately. Warning here would mean claiming something about a branch that may not run, which is not something anything in this compiler does.

7 · A scroll pair, broken the same way — warns

main { ppu.scroll = x var s: u8 = ppu.status ppu.scroll = y }

Warns (rule 1), in ppu.scroll's own words — an X scroll and a Y scroll, not a high byte and a low byte. See the wording page.

8 · The poll loop

main { while ppu.status < $80 { } // silent: no pair open ppu.mask = $1e } main { ppu.addr = $3f while ppu.status < $80 { } // warns: rule 1, carets on ppu.status ppu.addr = $00 } main { while ppu.status < $80 { } // warns: rule 2, the sync below waits a frame sync exact }

A condition is evaluated where its statement sits, so a read in one counts like any other. This matters because wait vblank is refused in this release — only `wait cycles` is supported yet — so a hand-written poll loop is the only vblank wait an author has besides sync exact.

9 · Two reads in one statement — one warning

main { ppu.addr = $3f var s: u8 = ppu.status + ppu.status ppu.addr = $00 }

One warning, carets on the first read. The first read is what breaks the pair; the second finds the latch already back at its first write.

10 · Both rules on one read — two warnings, latch first

main { ppu.addr = $3f var s: u8 = ppu.status sync exact }

Two warnings on the same line. They are two faults with fixes that point in opposite directions — move the read down past the pair, move it up past the sync — so the author has to see both.

11 · A read feeding the write that opens the pair — silent

main { ppu.addr = ppu.status ppu.addr = $00 }

Silent. Codegen emits the value before the store — LDA $2002 then STA $2006 — so the read happens while the latch is closed, and the write then opens a pair the next line closes. Correct, if peculiar.

12 · A compound assignment — warns

main { ppu.addr = $3f ppu.status += 1 ppu.addr = $00 }

Warns. ppu.status += 1 emits LDA $2002 before the store, so it really does reset the latch. Carets cover ppu.status, the destination — the width raster-1t9 chose for a compound assignment. (raster-xeo will refuse the write itself; until it does, this read is real.)

13 · A read in a global initializer — silent

var g: u8 = ppu.status main { ppu.mask = $1e }

Silent by construction: no pair is open and no sync exact follows. Unlike raster-hqh, where a ppu.data read in an initializer always warns, there is nothing to say here.

What was rejected

RejectedWhy not
Warn on every ppu.status readLoud on correct code — the latch-reset idiom (3) and a sprite-0 read (4) both warn, on every build, with nothing in this release able to silence a warning. And it misses case 2 entirely, because there is no ppu.status in that source.
The latch rule only, no flag ruleLeaves case 5 a silent lost frame in a language whose point is that you can count cycles. §9.1 names both side effects in one sentence.
Make the broken pair an errorDetection depends on rasterc recognising a pair, so a case nobody foresaw would break a build rather than nag. raster-6jr and raster-hqh both warn on a hazard of this shape.
Stay silent about sync exact's own readIt is the harder half of the hazard precisely because the compiler is the one reading $2002.
Warn across a { } (case 6)It would be the first thing in this compiler to warn about a path rather than a sequence.
Look further than the next statement for the flag ruleScanning the rest of the block fires on a read and a sync twenty statements apart, where the flag was going to be stale anyway.
Drop the scroll case, or use one neutral set of wordsA scroll pair breaks through the same latch, and “the second half” is vaguer than the ppu.addr wording already agreed.
