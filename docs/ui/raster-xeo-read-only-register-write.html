AGREED · raster-xeo

Writing ppu.status is refused

What the navigator chose, over two rounds. ppu.status is $2002, the one read-only port among the sixteen named registers: the PPU discards a store to it completely. Today rasterc accepts ppu.status = 0 and emits STA $2002 — three bytes and four cycles that do nothing, which is not nothing inside a timed block. This page is the rule and the states; the wording page beside it is every string.

What happened before this bead

main { ppu.mask = $1E ppu.status = 0 }
Compiled demo.raster -> demo.nes mapper MMC3 (4), NTSC fixed $E000-$FFFF, 145 of 8186 bytes used yours 13 bytes

Real output, run before the interview: exit 0, a ROM written, and three of those thirteen bytes discarded by the hardware.

Chosen · refuse it, a compile error

error: `ppu.status` cannot be written --> demo.raster:3:5 | 3 | ppu.status = 0 | ^^^^^^^^^^ $2002 is a read-only port = note: writing $2002 changes nothing on the PPU: it is a status port, and the CPU can only read it = note: there is no value that makes this store do something; delete the line error: could not compile demo.raster (1 error)

The build fails, no ROM is written, exit code 1. The write is wrong for every value, so no working program breaks; and it matches the rule raster-1t9 set for reads, so the register table answers both directions the same way and an author learns one rule instead of two.

Rejected — warn and build anyway. A dead store is harmless in a way a dead read is not, and nobody's build would break. But the four cycles are not harmless inside a timed block, which is the thing this compiler exists to get right; a warning that is always correct is one the author should never have been allowed to scroll past; and it would split the register table's answer, refusing reads and warning about writes.

Rejected — say nothing, document it. No new code and no false positive ever. But §9.1 already promises the compiler warns when a sequence violates a hardware requirement it can see, and it can see this one from the register table it already has.

The carets cover the destination

On ppu.status += 1 there is no = in the source to point at, so the refusal carries a note saying which operator wrote. Same shape raster-1t9 chose for the read a compound assignment makes.

error: `ppu.status` cannot be written --> demo.raster:2:5 | 2 | ppu.status += 1 | ^^^^^^^^^^ $2002 is a read-only port = note: `+=` writes its destination, so this writes $2002 = note: writing $2002 changes nothing on the PPU: it is a status port, and the CPU can only read it = note: there is no value that makes this store do something; delete the line

The note says only that the operator writes. It does not mention the read — the read of $2002 is legal and stays legal, and nothing here should imply otherwise. Rejected: "`+=` writes its destination after it reads", the exact mirror of the read refusal's note; true, not the point, and it invites the author to wonder about a read that is fine.

Chosen · a bad write and a bad read on one line are two errors

error: `ppu.status` cannot be written --> demo.raster:2:5 | 2 | ppu.status = ppu.mask | ^^^^^^^^^^ $2002 is a read-only port = note: writing $2002 changes nothing on the PPU: it is a status port, and the CPU can only read it = note: there is no value that makes this store do something; delete the line error: `ppu.mask` cannot be read --> demo.raster:2:18 | 2 | ppu.status = ppu.mask | ^^^^^^^^ $2001 is a write-only port = note: reading $2001 returns whatever was last on the PPU's data bus, not the last value written = note: keep what you wrote in a variable of your own and write the whole value error: could not compile demo.raster (2 errors)

Two independent mistakes on one line: fixing one does not fix the other, and the right-hand side may well survive into whatever the author writes instead. So the refused write still lowers its right-hand side, and the author sees both in one build rather than two. Rejected: reporting the write alone, on the argument that the statement is being deleted anyway — which is what makes the write-only error suppress the bank-select warning in raster-1t9. The difference is that these are two errors of equal standing.

Several of them, and what must stay silent

Every occurrence is reported, in source order, with its full notes each time. No deduplication, no "and 1 more" — the existing behaviour of every other refusal in the compiler.

main { var s: u8 = ppu.status // a read of $2002 -- legal, and stays legal ppu.mask = $1E // a write-only port, written -- always fine ppu.oam_data = $20 // $2004 reads and writes -- fine ppu.data = $0F // $2007 reads and writes -- fine }

Exit 0, no stderr at all, a ROM written. If any of these four lines goes red, the check has been attached to the wrong thing. Reading ppu.status in particular must stay silent: its side effects — clearing the vblank flag and the $2005/$2006 latch — are raster-bm1, a separate ranked bead, not this one.

A program that compiled yesterday and fails today gets no special framing — it is an ordinary error, exactly as raster-1t9's regressions are. Rejected: calling the change out in the build output.

Spec §9.5

raster-1t9 adds §9.5 with a one-column table and closes it "Every one of the sixteen may still be written. This is only about reads." — a sentence this bead makes false. The table gains a second column and the section is renamed "Which registers read and which accept writes"; the wording page carries the section in full. Rejected: keeping the one-column table and naming the exception only in prose — less ink, but a reader scanning the table for mmc3.bank_data would have to read underneath it to learn the register can be written.
