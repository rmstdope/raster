raster-fl4.5.3 — the decoded picture reaches the ROM and appears on screen

The agreed experience, one section per decision. Each section is the variant the designer chose.

Option A — the tiles are burned into the cartridge's tile ROM

What chrrom bank 0 { picture.tiles } says is what the cartridge gets: the tiles sit in the cartridge's own tile memory from power-on. Nothing copies them at start-up. Rows in blue are new or changed.

Source

asset image picture = png("art/picture.png") { kind: background palette: auto(4) dedup: true } chrrom bank 0 { picture.tiles } fn init() { ppu.mask = $00 wait vblank wait vblank load_palette(picture.palette) load_nametable(picture.nametable, picture.attributes) ppu.ctrl = $80 ppu.mask = $0A }

In the emulator

The emulator's header view shows "CHR ROM 8 KiB", matching the keyword. Start-up is instant. The 1792 bytes of tiles don't use any program space.

Option A — one row per tile bank

The build summary gives each chrrom bank its own row, naming what's in it and how full it is. Two pictures are shown here to make the shape visible.

This answers "how full is my tile memory". Once there are many banks the summary grows by one row per bank.

Option A — a picture placed second in a bank just works

Here the font's 48 tiles come first, so the picture's tiles start at tile 48. The compiler shifts the picture's nametable so it still points at the right tiles. You don't have to think about the order.

chrrom bank 0 { font.tiles, picture.tiles } fn init() { load_palette(picture.palette) load_nametable(picture.nametable, picture.attributes) // already points at tiles 48–159 }

rasterc demo.raster

Compiled demo.raster -> demo.nes chr 8 KiB ROM, 1 bank of 8 KiB bank 0 font.tiles + picture.tiles, 160 tiles, 2560 of 8192 bytes ...
picture, correct

There's one limit you can still hit: a picture's tiles must not cross the 256-tile line between the two pattern tables in a bank. That gets its own error (see the words drawing).

Option A — skipped bank numbers become empty banks

The source places tiles in bank 0 and bank 2 and nothing in bank 1. The cartridge gets three banks, and the empty one is shown in the summary.

chrrom bank 0 { picture.tiles } chrrom bank 2 { sprites.tiles }
Compiled demo.raster -> demo.nes chr 24 KiB ROM, 3 banks of 8 KiB bank 0 picture.tiles, 112 tiles, 1792 of 8192 bytes bank 1 empty bank 2 sprites.tiles, 64 tiles, 1024 of 8192 bytes ...

Bank numbers in the source mean what they say, so bank-switching code can rely on them. The empty bank still costs 8 KiB of cartridge, but the summary shows it.

Option A — refused: the picture is loaded but its tiles were never placed

The developer calls load_nametable(picture…) but forgets chrrom bank 0 { picture.tiles }. On screen that would show garbage or blank tiles.

asset image picture = png("art/picture.png") { kind: background } fn init() { load_palette(picture.palette) load_nametable(picture.nametable, picture.attributes) }

Option A — short: what is wrong, where, and the fix

The same shape as every error raster prints today: one headline, the line with the culprit underlined, and one help line. All four new errors are shown.

error: `chrrom bank 0` is full: 576 tiles, and a bank holds 512 --> demo.raster:7:17 | 7 | chrrom bank 0 { picture.tiles, font.tiles, sprites.tiles } | ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ 9216 of 8192 bytes | = help: move some of these to `chrrom bank 1`
error: `font.tiles` crosses into the second pattern table --> demo.raster:7:32 | 7 | chrrom bank 0 { picture.tiles, font.tiles } | ^^^^^^^^^^ tiles 240–287; a picture must sit within tiles 0–255 or 256–511 | = help: give `font.tiles` its own bank, or place it first
error: `load_palette` takes a palette, not tiles --> demo.raster:10:18 | 10 | load_palette(picture.tiles) | ^^^^^^^^^^^^^ this is `picture`'s tiles | = help: did you mean `picture.palette`?
error: `load_nametable` takes a nametable, then its attributes --> demo.raster:11:20 | 11 | load_nametable(picture.attributes, picture.nametable) | ^^^^^^^^^^^^^^^^^^ this is `picture`'s attributes | = help: write `load_nametable(picture.nametable, picture.attributes)`

Concise, so an experienced NES developer reads each in a glance. Someone new to the NES has to look up "pattern table" elsewhere.

Option B — a warning when rendering is plainly on

When the compiler can see, in the same function, a ppu.mask write that turns rendering on and nothing turning it off before the call, it warns. Where it can't tell, it stays quiet.

fn init() { ppu.mask = $0A // rendering on load_nametable(picture.nametable, picture.attributes) }
warning: `load_nametable` runs while rendering is on --> demo.raster:3:5 | 2 | ppu.mask = $0A | -------------- rendering turned on here 3 | load_nametable(picture.nametable, picture.attributes) | ^^^^^^^^^^^^^^ 1024 writes cannot finish inside one vblank; the screen will tear | = help: call it before `ppu.mask = $0A`, or set `ppu.mask = $00` first Compiled demo.raster -> demo.nes (1 warning)

Catches the commonest version of the mistake before the emulator does. Calls from another function, or after a loop, go unchecked.
